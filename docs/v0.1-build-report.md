## Venue licence finding

No clear redistribution permission was found in the official CCF directory's
copyright notice or the ICORE portal and its linked four-page usage guidance.
The implementation follows the brief's fallback: **do not bundle the data**;
download the official publications at deployment time into the user's private
configuration directory, then upload to their own KV namespace.

The CCF introduction links the 2026 PDF; category HTML pages still carry older
publication dates, so the downloader uses the PDF's edition year. ICORE exposes
an explicit CSV export with its source edition. Rank source URLs and years are
retained; DBLP is never queried. Official documents were inspected outside tests;
a local parse produced 558 CCF rows (552 with DBLP stream links) and 987 ICORE
rows. The downloaded documents and parsed table were removed afterwards. Only
tiny invented venue fixtures are tracked.

This is a conservative distribution decision, not legal permission for every use.
The detailed primary-source links and scope are in
[venue-data-licence.md](venue-data-licence.md).

## Incomplete or uncertain

- **P5 data:** the referenced local measurement repository contains its report and
  sampling scripts, but no original 600-paper sample or recorded S2/OpenAlex
  title-query replies were found. An existing snapshot location was requested.
  The evaluation tests use explicitly synthetic cases to verify the harness;
  their success does not establish real-world coverage.
- **P5 year discrepancy:** the original measurement uses ICCV 2023, with the
  other venues sampled from 2024. The evaluator preserves this exception and
  requires 15 venues with 40 unique papers each and seed 7.
- **CI gate:** ordinary code-change CI records absent P5 data as an explicit
  warning and uploads an `unverified` report. Once a snapshot exists, a score
  below 90% fails. A manual run with `require_evaluation: true` also fails if the
  snapshot is missing. Ordinary green CI is therefore not release acceptance.
- **Upstream compatibility:** tests use synthetic protocol-shaped fixtures, not
  newly recorded live responses. Actual source responses, keys and quotas have
  not been exercised. CORE's detailed v3 documentation endpoint was inaccessible
  during the build; its live compatibility especially needs checking.
- **Venue extraction:** the PDF parser handles the inspected layout and wrapped
  rows, but extraction accuracy across all cells was not exhaustively labelled.
  Missing DBLP links remain unknown. Names differing between CCF and ICORE can
  remain separate fuzzy matches. Spot-check representative journals, conferences,
  wrapped titles and renamed venues before release.
- **Deployment:** no clean Cloudflare account test, remote MCP-client test,
  free-tier feasibility measurement or timed ten-minute onboarding test occurred.
  These remain maintainer tasks, as required by the prohibition on deployment.
- **Bounded results:** author publication evidence can be partial; reviews stop
  at 1,000 forum notes and flag truncation; recommendations cover at most 500
  results. Source failures and missing venue data remain visible.

## Exact maintainer steps

These are instructions for future maintainer action; none were executed here.

1. Supply the original sample and lawful, scrubbed upstream response recordings
   in the [documented snapshot format](../eval/README.md). Run
   `npm run test:eval -- path/to/recorded-600.json`; require at least 540/600
   matches and inspect per-venue failures. Preserve the real arXiv observations
   and the sampling provenance. Do not replace missing data with generated hits.
2. Obtain a Semantic Scholar key (recommended), an OpenAlex key if desired, and
   a CORE key for OA enrichment. Use the provider links in the README. Recheck
   provider limits, Cloudflare availability/pricing and venue terms. Seek explicit
   permission before distributing any ranking table.
3. On a clean Cloudflare account, run `npm ci`, `npm run build`, then
   `node dist/cli/index.js deploy`. Complete Wrangler authentication yourself;
   enter source keys only at private prompts. Verify the downloaded table and
   resulting deployment URL. Check `status`, then run `pair` and connect a real
   remote MCP client. Exercise all seven tools, key rotation and client revocation;
   confirm the old client loses access. Use `destroy` only for the disposable test
   deployment after these checks.
4. Run `npm test`, `npm run test:coverage`, `npm run typecheck`, `npm run lint`,
   `npm run format:check`, `npm run test:worker` and the recorded-data acceptance
   gate. If desired, run the separate opt-in live checks with your own keys.
   Inspect the npm package with `npm pack --dry-run --ignore-scripts` and verify
   the clean-account onboarding time before declaring v0.1 ready.
5. Only after all acceptance checks pass, confirm ownership of the npm name and
   version, authenticate with `npm login`, and publish with `npm publish
   --access public`. Review any Git push/tag or registry listing separately;
   this build has made no remote repository or registry changes.
